Design Principles

The Design Principles

These are the thirty-nine ideas that govern every decision in CocoPlus. They are worth understanding not just as rules — but as the reasoning behind them.

These are the thirty-nine ideas that govern every decision in CocoPlus. They are worth understanding not just as rules — but as the reasoning behind them.

A principle without a reason is just a constraint. With a reason, it becomes a compass.

1. Native First, Always

Principle

CocoPlus uses only what Coco already provides: skills, subagents, hooks, slash commands, and AGENTS.md. Nothing external. No third-party services bolted on, no external databases, no runtime dependencies beyond the Snowflake connection Coco already manages.

The reason for this is not purity — it is reliability. Every external dependency is a failure vector that lies outside your control. A cloud service rate-limits under load. A database pool exhausts at midnight. An API changes its response format without notice. When any of these happen inside CocoPlus, the developer has to debug a distributed system problem to understand why their AI plugin failed.

Native constructs fail in ways you can read and understand. A hook script that fails leaves an error message in a format you recognize. A skill file that has a logic error is a file you can open and read. The failure modes are local, legible, and fixable without calling anyone.

If a feature requires breaking this principle, the feature does not belong in CocoPlus.

Applied in CocoPlus

CocoPlus ships as Coco-native skills, agents, hooks, commands, templates, and AGENTS.md rules. Runtime behavior stays local and file-based so failures are legible inside the project instead of depending on outside services.

2. Structure Enables Flow

Principle

The CocoBrew phases feel like overhead — until the moment you realize you haven't written a spec for your last three AI sessions and the outputs are inconsistent in ways you can't trace.

Structure is not the opposite of speed. Unstructured development feels faster at first because you're skipping steps. Then you spend twice as long on the steps you skipped — debugging misaligned expectations, re-running tests you didn't design, shipping code that doesn't match what the stakeholder asked for.

The phases in CocoBrew are cognitive handrails. Each phase enforces a mental discipline that the next phase depends on. You can't write a good test if you don't have a spec defining success. You can't do a meaningful review if you don't have tested code. You can't ship responsibly if your review is open.

This sequencing is not bureaucratic. It is the shape that good development naturally takes when you're paying attention.

Applied in CocoPlus

CocoBrew turns work into Spec, Plan, Build, Test, Review, and Ship phases. Each phase writes durable artifacts that the next phase reads, so speed comes from clear handoffs rather than skipped thinking.

3. Inspect Before Act

Principle

Acting on stale context is one of the most reliable ways to produce wrong outputs.

Before any agent executes SQL, it should understand the schema it's operating on. Before any deployment, it should understand the target environment. Before any migration, it should understand the current state of what it's migrating from.

The Environment Inspector embodies this as a feature. But the principle applies everywhere in the system. CocoHarvest reads the approved plan before decomposing it. The Safety Gate reads the SQL before allowing it to execute. Skills read the current state from .cocoplus/ before taking action.

Inspection has a cost. A 30-second environment scan uses tokens and time. But the cost of inspection is fixed. The cost of acting on wrong assumptions is variable — and the upper end of that variable is "you dropped the wrong table."

The inspection habit is cheap discipline that prevents expensive mistakes.

Applied in CocoPlus

Environment Inspector, Safety Gate, CocoHarvest, and project skills read the current schema, plan, flow state, or lifecycle files before acting. The plugin treats inspection as the required precondition for Snowflake and project mutations.

4. Evidence Over Assertion

Principle

A subagent that reports completion is not done. A subagent whose checkpoint files exist and contain valid data — that one is done.

This distinction matters because language models are very good at describing what they intended to do and somewhat less reliable about verifying that they actually did it. The CocoFlow checkpoint system is designed to make completion measurable rather than reportable.

Stages emit specific files as their completion evidence. Downstream stages read from those files, not from the previous stage's session context. The Safety Gate re-validates before allowing Ship. The Review phase signs off on concrete artifacts.

The system is designed to make assertions costly and evidence cheap. Not because any individual agent is untrustworthy — but because the incentive structure of a well-designed system should reward producing evidence, not reporting claims.

Applied in CocoPlus

CocoFlow checkpoints, Safety Gate checks, CocoSentinel approvals, CocoContract evidence, and review artifacts turn completion into observable files and validation results instead of accepting agent narration as proof.

5. Hard Gates for Irreversible Operations

Principle

Some mistakes cannot be undone. Dropped tables. Truncated schemas. Deleted rows without a WHERE clause.

For these operations, a warning is insufficient. A language model that is prompted carefully follows its instructions most of the time. Most of the time is not acceptable for irreversible operations on production data.

Hard gates are technical enforcements that operate before any reasoning happens. The Safety Gate's PreToolUse interceptor fires before the SQL reaches Snowflake. It does not ask the language model for permission. It reads the SQL, recognizes the pattern, and blocks the call. This cannot be bypassed with a clever prompt.

For recoverable mistakes — wrong logic, suboptimal queries, missing edge cases — advisory guidance is appropriate. Soft guidance informs, does not block.

The distinction between hard and soft is architectural. Confusing them — making hard things soft, or making soft things hard — degrades the system in both directions. Soft gates on irreversible operations give false confidence. Hard gates on recoverable mistakes create friction that serves nobody.

Applied in CocoPlus

Safety Gate blocks or confirms destructive SQL before execution, while advisory systems such as Code Quality Advisor and Context Mode stay non-blocking. CocoPlus separates irreversible boundaries from recoverable guidance.

6. Progressive Disclosure

Principle

Load the minimum context needed for the current task. Not slightly less. Not roughly the right amount. Exactly the minimum.

AGENTS.md is capped at 200 lines because every character in it is loaded into every session. Skills are loaded on demand because they contain detailed implementation logic that most sessions don't need. Monitors run per-stage because global monitors create context overhead that accumulates across every stage.

The temptation is always to add more "just in case." Just-in-case context becomes noise. Noise makes it harder for the agent to reason about the signal. A skill that loads 600 lines of context to execute a 30-line workflow is a skill whose design should be questioned.

The hard limit is a forcing function for clear boundaries. If AGENTS.md can only hold 200 lines, you have to decide what belongs there and what belongs in the warm layer. That decision-making process is valuable in itself — it forces you to articulate what the ambient context of a session actually needs to contain.

Progressive disclosure is how the system scales. At session 10, it works. At session 200, it still works, because the context budget is managed rather than exhausted.

Brevity in skill files turns out to be more than an aesthetic preference — it's measurable. Internal evaluation found that a skill file padded with explanatory methodology prose raised output regression rates from roughly 6% to roughly 10% compared to a compressed version carrying the same active instructions. Longer prompts dilute the weight of each instruction; a model can partially follow a long explanation in a way it can't partially follow a short directive. The test when compressing a skill file isn't "does this feel succinct" — it's "if I cut this explanation in half, does output quality improve or degrade."

Applied in CocoPlus

AGENTS.md is kept compact, skills load only when invoked, monitors run at targeted lifecycle points, and CocoPull/CocoSession preserve dense handoffs so context budget is spent on the current task.

7. Classify Failure Before Retry

Principle

When a stage fails, the failure must be understood before it is addressed.

Blind retry is not a strategy — it is an absence of strategy dressed up as action. Running the same failing stage again without understanding why it failed produces the same failure, or a different failure, unpredictably. Either way, you learn nothing.

Failure classification is the first step. Did the checkpoint file not get created? Did it get created with invalid content? Did the SQL error? Did the test fail? Each of these failure types has a different root cause and a different repair.

The CocoFlow loop construct exists for structured retry after classification. A loop that retries up to three times is appropriate after you've identified that the failure is transient — a timeout, a connection issue. A loop that retries three times on a logic error produces three documented failures instead of one.

Logging the classification is what makes the Memory Engine valuable. CocoCupper can identify patterns in failure classifications across sessions. "Stages that involve NotebookExecute fail on checkpoint validation 40% of the time due to notebook output formatting" is a pattern worth knowing. Unclassified retries produce no learning.

Applied in CocoPlus

CocoFlow retries are tied to classified failure modes, not hope. Stage status, checkpoint validation, hook logs, and CocoCupper observations preserve why something failed so repair can target the cause.

8. Institutional Memory Over Rediscovery

Principle

Every session should leave the project in a better-documented state than it found it.

This is not a nice-to-have. It is the difference between a project that gets smarter with time and one that resets with every new session.

The Memory Engine captures decisions as they happen. CocoCupper identifies patterns after sessions complete. CocoGrove stores the patterns worth keeping permanently. The three-layer memory architecture exists because different knowledge has different durability: some decisions are relevant for today's session, some for the next month of sessions, and some indefinitely.

An error that was encountered and resolved is worth recording — not because you are proud of the error, but because the next developer (or the next AI agent, or you in six months) should not have to rediscover the same solution. A schema pattern that worked well is worth promoting to CocoGrove so it becomes the default approach, not the hard-won exception.

The cost of documentation is paid once. The benefit of not re-discovering something is paid every time it would have been re-discovered.

Applied in CocoPlus

Memory Engine, CocoCupper, CocoGrove, CocoWisdom, CocoRecall, and CocoDiary capture decisions, rejected approaches, reusable patterns, and session understanding so future work starts from what the project already learned.

9. Token Economics as Architecture

Principle

Token budgets are not constraints to work around. They are parameters that shape the system's design.

CocoPlus makes explicit model assignments across the system: Haiku for pattern recognition (CocoCupper), Haiku with Sonnet escalation for analytical tasks (Data Analyst, BI Analyst), Sonnet for execution and reasoning (most personas), Opus for strategic decisions (CDO). These are not preferences — they are architectural decisions about where depth is required and where efficiency is sufficient.

The AGENTS.md limit, the on-demand skill loading, the per-stage monitor activation — all of these are token economics expressed as design constraints. They ensure that the system is as useful at session 200 as it is at session 1, because context budget is managed at every layer.

When designing a new feature, the first question is not "what should it do" — it is "what does it cost to do that, and is the cost justified at scale?" A feature that works beautifully for the first twenty iterations and breaks the context budget by iteration thirty is not a well-designed feature.

Applied in CocoPlus

CocoMeter, role-based model tiers, ACRR calibration, cost categories, and skill surface budgets make token and credit cost visible design inputs. CocoPlus treats model depth and context size as architecture, not afterthoughts.

10. Isolation Prevents Contamination

Principle

CocoHarvest agents run in isolated git worktrees. CocoFlow stages marked as isolated start with clean context. Unverified output from one stage does not become assumed truth in the next.

Isolation is not just about parallelism. It is about correctness.

When one stage contaminates the next with incomplete or incorrect assumptions, the error propagates. By the time you notice it — at Stage 4, or Stage 6, or during Review — the contamination has compound interest. Debugging requires tracing back through multiple stages to find where the wrong assumption was introduced.

Isolated stages prevent this. Each stage has explicit inputs (the files and checkpoints from prior stages) and explicit outputs (the checkpoint files it produces). The interface is clear. A failure is localized — it is in this stage, not diffused through the system.

The cost of isolation is real: more explicit file-passing, more checkpoint definitions, more deliberate context management. It is always lower than the cost of debugging a contaminated failure.

Applied in CocoPlus

CocoHarvest worktrees, isolated CocoFlow stages, explicit checkpoint files, retained proposals, and evaluator lockout keep work products from contaminating independent review or downstream execution.

11. Personas Are Contracts

Principle

A persona is not a suggestion for how to approach a task. It is a specification of who handles the task, what tools they have, how they operate, and what model reasons on their behalf.

These specifications are locked. The Data Steward operates in plan mode because autonomous execution defeats the purpose of governance review — someone who can take action without prompting is not a check, they are a participant. The CDO uses Opus because the cost of Opus is appropriate for decisions at the level of strategic architecture.

Persona contracts matter because CocoPlus is a team system. When you assign a task to a persona, you know exactly what will happen: which tools will be available, which model will reason, which output format to expect. That predictability is the value of the contract.

A persona whose contracts can be arbitrarily overridden is a persona without identity. Identity in a specialist agent is not a personality quirk — it is the source of the specialist's value. Override the contract, and you have a generalist again.

Applied in CocoPlus

The fixed persona roster and dynamic personas declare tools, model expectations, scope, and handoff behavior. Routing honors those contracts so a Data Steward, CDO, or Data Engineer means a predictable operational boundary.

12. The Plugin Serves the Developer

Principle

Every feature must produce visible, direct value to the developer working in the terminal.

This sounds obvious. It is often violated.

Features that add process overhead without developer benefit are not features — they are compliance theater. A feature that ensures the AI's session is auditable but provides the developer nothing concrete is a feature that serves a process, not a person.

Before any feature is built, the test is: does the developer experience value directly? Does it save them time? Does it prevent an error they would have made? Does it produce an artifact they actually want? If the answer is "it helps governance" or "it satisfies the audit trail," the next question is: does the developer experience that help, or does it happen invisibly behind them?

CocoPlus is not a governance layer. It is a productivity layer. The difference is where the value lands. Governance lands in reports. Productivity lands in the developer's experience of doing the work.

If CocoPlus ever starts to feel like something to work around rather than something to work with, this principle has been violated.

Applied in CocoPlus

Every feature is expected to give the developer a visible benefit: safer SQL, better handoffs, clearer costs, stronger review, faster retrieval, or less repeated work. Governance features surface actionable state rather than hiding in reports.

13. Look Up Before Inferring

Principle

When an authoritative source exists — a catalog of valid values, a documented API contract, a structured reference file — query it before guessing. Inference is the fallback for what can't be looked up, not the default path that happens to work most of the time.

Snowflake function signatures, Cortex API parameters, supported data types, and the draw.io shape catalog are all lookable. When CocoSketch needs the correct shape=mxgraph.* string for an AWS service icon, it queries the shape index rather than guessing from the service name. A wrong shape string renders as a blank box — the visual output silently lies. A correct one renders the intended icon.

Before asking a model to produce a specific technical value — a function name, a parameter, a type identifier, a command flag — ask whether that value exists somewhere readable. If it does, read it. This ordering is the difference between output that's reliable and output that's merely plausible.

Applied in CocoPlus

CocoSketch shape lookup, Snowflake inspection, Cortex function references, validation scripts, and command specs prefer structured sources over model inference whenever a correct value can be read directly.

14. Scope Boundary as Feature

Principle

Every CocoPlus capability defines what it is not for, with a clear redirect to what should be used instead. This isn't a disclaimer — it's a precision affordance.

A tool that claims to do everything signals it understands nothing about tradeoffs. CocoSketch is the commit-grade visual artifact tool: quick whiteboard diagrams go to Mermaid, interactive exploration goes to CocoMap, complex developer-authored diagrams go to CocoSketch. Each boundary routes the developer to the better tool for their actual need.

The same discipline applies system-wide. CocoAudit is for regulated compliance trails, not general session logging. CocoTrace is for requirements coverage, not general file-change tracking. CocoReview is for code artifacts, not specification documents. A "when NOT to use" section in a skill's frontmatter carries as much weight as the "when to use" section — scope boundaries are what stop a feature from drifting into adjacent responsibilities it was never designed for.

Applied in CocoPlus

Skills and feature docs define when not to use a capability and point to the better tool. CocoSketch, CocoAudit, CocoTrace, CocoReview, and related features keep their responsibility boundaries explicit.

15. Two Consumers, Two Output Modes

Principle

When an output will be read by both a machine agent and a human developer, one format optimized for neither is a false economy. The two have structurally different requirements.

Machine-optimized output maximizes information density — no section headers, no prose transitions, no narrative framing. Every token carries information. This is what CocoHarvest loads as stage input and what CocoFlow passes between pipeline steps; formatting prose in that path spends token budget on structure the consuming model gets no value from.

Human-optimized output prioritizes comprehension — a summary at the top, section headers for navigation, prose transitions between dense sections. This is what a developer reads to verify a distillation or review a report at a glance.

CocoPull's two modes (compact default, --human flag) embody this directly, as does CocoSketch's preview PNG versus final PNG. The distillation logic stays shared; only the formatting layer branches at the last step based on who's reading. Never optimize for the more forgiving consumer — the human — and hand the result to the less forgiving one, the LLM context window.

Applied in CocoPlus

CocoPull compact and human modes, dashboard views, checkpoint JSON, markdown reports, and review outputs use separate presentation paths for machines and people while preserving the same underlying facts.

16. Minimum Viable Surface

Principle

Every Cortex function, CocoFlow stage, and plugin construct should be the minimum surface area that credibly solves the stated problem — sufficient, and no larger than sufficient.

This counters a real bias: the path of least resistance for a language model is to generate. Asked to solve a simple problem, a model often produces a complex solution, because complexity is more available in its training distribution and looks more like effort. CocoLean makes the countermeasure explicit — the six-rung decision ladder (deterministic rule → native built-in → existing UDF → single AI_COMPLETE call → minimum-line function → full Cortex function) runs before any new function gets written, and stops at the first rung that answers the need.

The same logic applies to CocoFlow stages (a single well-scoped LLM call beats three chained synthesis steps that produce the same output quality) and to plugin constructs themselves (a skill loading in 150 tokens beats an equivalent one loading in 300). The constraint is equivalence, not degradation — minimum surface never means less capability, only no excess.

This principle never applies to trust boundaries, data loss prevention, security controls, regulatory compliance, or error handling that prevents silent data corruption. Those aren't excess — they're the safety surface everything else sits on. The question is whether a stage needs four synthesis steps, never whether a trust boundary check is YAGNI.

Applied in CocoPlus

CocoLean, CocoBehavior, and CocoReview complexity audit enforce the smallest sufficient function, stage, or skill surface. Safety, compliance, and data-loss boundaries remain protected carve-outs rather than YAGNI targets.

17. Outcome Before Evidence

Principle

Declare what correct behavior looks like before the generator begins. The outcome contract must exist as an independent, committed artifact before any spec, plan, or build activity produces the function it will evaluate.

This addresses a failure mode invisible from inside the system that produces it: when an agent generates a function and then evaluates it against criteria the same agent authored, the evaluation is self-confirming by construction. The generator's intentions were present the whole time — evaluation criteria derived after the fact cannot be independent of the output they're judging. A more rigorous self-authored evaluation just produces a more rigorous tautology. The question was never the quality of the evaluation — it's the independence of the oracle.

"Before" means structurally before: the contract is declared before $spec or $build runs, committed to version control ahead of generation, and authored by the developer or a designated oracle-author who is not the generating agent. The commit timestamp is what proves independence. Evidence is then classified by epistemic strength — real-endpoint execution with an externally verifiable result is the only tier sufficient for production certification; evaluation that shares session context with the generator is explicitly insufficient, no matter how thorough it reads.

This principle is a close relative of Evidence Over Assertion (4) — that one says don't assert what you haven't measured, this one says don't measure against criteria you invented after building the thing you're measuring. CocoContract is the operational instrument: $contract init is how the oracle gets declared and committed before generation begins, and the stop hook on $ship is what makes this an architectural invariant instead of a suggestion.

Applied in CocoPlus

CocoContract requires outcome criteria and evidence hierarchy before generation and gates Ship on independent proof. The evaluator cannot quietly invent the success standard after seeing the generated artifact.

18. Declarative Agency Boundary

Principle

A pod's authority is fully defined by what it explicitly declares it will do and what it explicitly declares it will not do. Undeclared territory does not default to "available" — it defaults to "not my concern." Explicit exclusion is as architecturally load-bearing as explicit inclusion.

In a single-pod system, scope is defined by what the pod includes. In a multi-pod system, scope is defined by the intersection of every pod's inclusions and exclusions. Two undeclared territories facing each other produce overlap by default — both pods may reasonably conclude a concern is theirs, and both fire, producing duplicate or contradictory guidance on the same issue. Two explicit exclusions facing each other produce a clean boundary by design, with no ambiguity for either pod to resolve at runtime.

Every CocoPod definition carries an excludes: field alongside its capability description, naming the concern classes it does not own. CocoPivot's scope anomaly detection depends entirely on this — a pod without a declared exclusion boundary cannot be evaluated for scope discipline, because there is nothing to check its output against. This is why the field is required for any pod running in a parallel workflow: without it, the convergence step has no way to tell a legitimate finding from scope creep.

Applied in CocoPlus

CocoHarvest pods and dynamic personas declare owned and excluded concern classes. CocoPivot uses those declarations to detect overlap, gaps, and scope drift during convergence.

19. Metering as Governance

Principle

Cost visibility is not just a dashboard concern. In an AI development system, metering is a governance boundary: it explains who used which model, which workflow caused the spend, which cost center owns it, and whether a change shifted cost from tokens to warehouse compute.

CocoMeter therefore treats chargeback facts as evidence. It separates token and warehouse credits, preserves attribution to stages and users, exposes unmapped cost centers instead of hiding them, and strips infrastructure-only system reminders before prompt persistence. A cost report that cannot explain its provenance is not governance — it is decoration.

This principle also applies to model tier declarations. A stage that asks for ultra must not silently fall back to regular, because that changes both cost and quality semantics. The developer should see the unavailable tier and decide what to do.

Applied in CocoPlus

CocoMeter Enhanced, chargeback scripts, request maps, model tier resolution, and reconciliation artifacts make token spend, warehouse credits, cost centers, and actual served models explainable.

20. Declared Boundaries Over Assumed Scope

Principle

Agent authority, quality thresholds, action permissions, and evaluation criteria work when they are explicitly stated before action. They degrade when they are inferred at runtime, discovered mid-execution, or explained afterward to fit what already happened.

Undeclared scope is scope that can be interpreted to fit whatever happened. Declared scope is accountable before the fact: a boundary stated before action is a constraint; a boundary stated after action is a rationalization.

Applied in CocoPlus

CocoFlow HITL/AFK classification, CocoPivot excludes: scopes, CocoSpec and CocoContract pre-commitment, CocoSentinel action tiers, CocoStyle convention profiles, CocoLex vocabulary, and CocoAdversary exclusions declare boundaries before the system acts on them.

21. Persistence as the Precondition for Trustworthiness

Principle

A system that stores critical state only in transient session memory cannot be trusted by anyone who was not present when the state was produced. Trust is a property of the record, not of the memory.

Any decision, approval, quality gate result, or evaluation that a future agent, developer, or audit may rely on must be written to a durable, integrity-protected record before the session ends.

Applied in CocoPlus

CocoAudit append-only records, SHA-bound approvals, CocoContract evidence hashes, doc-state staleness graphs, quality watermarks, CocoFlow crash-recovery checkpoints, LEARNINGS records, and CocoWisdom stores make past claims verifiable.

22. Honest Uncertainty as a First-Class Outcome

Principle

A quality system that recognizes only verified and failed outcomes is structurally dishonest when evaluation cannot be performed in the current environment. UNTESTABLE HERE is not a failure; it is a disclosure.

Known evaluation limitations are not documentation footnotes. They are live gap records that tell the operator what was being evaluated, what prevented evaluation, what evidence would close the gap, and whether the limitation is persistent or session-specific.

Applied in CocoPlus

CocoContract, CocoSentinel, CocoForge adversarial self-checks, CocoMeter reports, lifecycle/known-gaps.json, $adversary gap, and CocoDiary's open-risk section surface verified, refuted, and untestable-here states instead of collapsing them into pass/fail theater.

23. Understanding Is the Work, Not Its Residue

Principle

A session produces artifacts and understanding. The artifacts survive in git; the reasoning, risk discoveries, operator decisions, and changed mental model disappear unless captured before the session ends.

CocoDiary, CocoWisdom, audit summaries, and session handoffs follow the never-invent rule: a shorter true record is better than a longer plausible one. Documentation captures what was learned, not what the agent wishes had been learned.

Applied in CocoPlus

CocoDiary, session handoffs, audit summaries, and wisdom records capture decisions, risks, operator choices, and learned context using the never-invent rule, so continuity preserves understanding as well as files.

24. Context Isolation Is a Governance Property, Not a Configuration Option

Principle

An evaluator that can see or alter the work it reviews is no longer independent. Isolation is not a strict-mode preference; it is the condition that makes review meaningful.

ReviewerLockout, CocoReview, CocoContract, CocoSentinel, CocoForge critic passes, Leviathan coordination channels, and PII governance all depend on explicit, auditable channels rather than ambient context bleed.

Applied in CocoPlus

ReviewerLockout, isolated critic passes, proposal settlement, PII governance, and CocoForge critic boundaries keep generators, reviewers, and operators separated through auditable channels.

25. Stated Is Not Enforced

Principle

A rule in documentation is an aspiration until a deterministic check, hook, or structural gate enforces it. Operators must be able to tell whether a constraint is machine-enforced, hook-guarded, or guidance-only.

CocoSentinel findings, governance hooks, shadow rollouts, and coding-agent instructions label enforcement tier explicitly so the gap between statement and enforcement stays visible.

Applied in CocoPlus

Validation scripts, hooks, gate metadata, shadow policies, and documentation label whether a rule is enforced structurally, observed by hooks, invoked by skills, or only documented guidance.

26. Consolidation Is Not Capture

Principle

Capturing knowledge records an observation. Consolidating knowledge maintains the record by merging duplicates, resolving contradictions, pruning stale entries, and indexing the result for retrieval.

CocoRecall, CocoDream, Memory, and hygiene loops treat consolidation as a scheduled maintenance obligation. A system that captures forever and consolidates never is an accumulator, not a memory.

Applied in CocoPlus

CocoRecall indexing, CocoDream consolidation, CocoHygiene archives, wisdom routing, and memory maintenance distinguish fresh capture from later cleanup, deduplication, and stale-record handling.

27. Context Rot Is an Architecture Problem

Principle

Context rot is the quiet degradation where accumulated tokens reduce the effective weight of earlier instructions. It is not solved by telling the agent to pay more attention. It is solved by architecture: fresh context windows for independent checks, predicate-style persistent state, and skill surface budgets that avoid loading unnecessary instructions.

If the system needs to remember something important, it must write it in a form that survives context accumulation. CocoSession's CONTEXT.md predicates and CocoConsole's Skill Surface Budget make this visible and enforceable.

Applied in CocoPlus

CocoSession writes predicate CONTEXT.md, PROGRESS.md, task queues, budget state, and status files so important state survives context growth and can be read cold by a future session.

28. Proposals Before Commits

Principle

Agent work that can affect Snowflake objects, committed SQL, or pipeline configuration is safest as a retained proposal until the operator settles it. Reversibility before commit is categorically safer than undo after commit.

This principle does not slow every workflow. It applies where the stage opts into proposal mode because its output crosses a meaningful boundary. Autonomy may prepare the change; it may not convert the proposal into a live effect without settlement.

Applied in CocoPlus

CocoFlow retained proposal mode stores Snowflake writes and pipeline changes under .cocoplus/proposals until the operator explicitly accepts or discards them with flow settlement.

29. Actuator Cost Is Monotonic

Principle

Every rule has a cheapest sufficient actuator. A hook fires only when the guarded action fires. A skill loads only when invoked. A structural agent rule loads for a session class. Standing context loads every time, whether relevant or not.

The cheapest actuator sufficient for the job is the right actuator. CocoRetro and CocoHygiene exist to keep the system honest: they classify failures, measure wasted effort, and propose fixes at the lowest layer that can actually prevent the recurrence.

Applied in CocoPlus

CocoRetro and CocoHygiene push recurring fixes toward the cheapest sufficient actuator: a hook when a structural guard is needed, a skill when invocation is enough, and standing context only when it truly must be ambient.

30. The Permission Floor Is Not the Permission Ceiling

Principle

A permission level observed at session start is not a guarantee for the rest of the session. Governance must check the live permission state at the point of enforcement.

This is why CocoSentinel logs bypass-safeguard state after tool use, why RBAC escalation to ACCOUNTADMIN is blocked by a PreToolUse hook by default, and why CocoConsole displays current governance posture rather than assuming the launch state still holds.

Applied in CocoPlus

PreToolUse and PostToolUse governance checks inspect live permission posture, RBAC escalation, bypass safeguards, and private-history state at enforcement time rather than trusting a session-start assumption.

31. Divergence Requires Isolation

Principle

A single context window anchors on its own previous text. Asking one model call to produce and evaluate multiple options does not create real independence; the options have already contaminated one another.

CocoFlow's diverge-then-focus path uses isolated planning branches and a separate critic pass. The output must surface shortlist, named traps, design-space clusters, and a labeled non-obvious viable option so the developer can see more than the familiar first answer.

Applied in CocoPlus

CocoFlow branch planning, isolated generation calls, separate critic passes, and CocoKlatch participants create real divergence by separating context at the API and artifact boundary.

32. The Harness Is the Optimization Surface

Principle

For complex agent workflows, the separable control layer around the model is where optimization is most attributable: context assembly, tool exposure, generation settings, orchestration topology, memory behavior, and output processing.

CocoPod configuration now names those dimensions explicitly in cocoplus.toml [harness]. If accuracy improves across harness iterations, keep tuning the harness. If it plateaus immediately, the bottleneck is probably model capability, evaluation quality, or task framing.

Applied in CocoPlus

cocoplus.toml names harness dimensions such as context assembly, model roles, tool exposure, generation controls, state persistence, and output extraction so tuning can be attributed to the right surface.

33. Deterministic Computation Belongs in Code, Not in Tokens

Principle

If a task has a correct answer computable from available data, it belongs in a script. SQL validation, schema parsing, function signature extraction, scope classification, and artifact existence checks should not be narrated into being by a model.

SKILL.md routes the workflow, scripts compute deterministic facts, and references load only when needed. CocoBrew's distribution gate and observer loop enforce that separation for project-local skills and marketplace candidates.

Applied in CocoPlus

Project scripts such as validators, complexity estimators, artifact checks, status healers, chargeback helpers, and flow readers compute deterministic facts outside the model context.

34. Enforce Budgets at Natural Seams, Not Mid-Step

Principle

Cost is recorded when usage data lands. Mid-call, the system does not yet know the final spend. Killing an in-flight stage at an estimated boundary risks losing both the compute already spent and the deliverable that would have justified it.

CocoPlus enforces cost budgets at natural boundaries: between iterations, after stage completion, and before dispatching new work. A reserve window is held back for landing work such as final evaluation, commits, PROGRESS.md updates, and handoff notes. Reserve is not slack; it is the budget for ending cleanly.

Applied in CocoPlus

CocoSession cost budgets stop new dispatch at stage boundaries, reserve landing budget for handoff and final checks, and record execution, coordination, and landing spend separately.

35. One Vocabulary, Two Homes

Principle

When two stores describe the same state, they should share one vocabulary. A local CocoPod state file and a CocoConsole row should not need translation between "done," "complete," and "finished." Translation turns recovery into interpretation.

The distinction between completed, exited, and failed is load-bearing. completed means the goal was met. exited means the system stopped structurally, such as budget, timeout, or operator stop. failed means something broke and needs investigation.

Applied in CocoPlus

CocoSession, CocoFlow, CocoPod state, and CocoConsole use the same terminal status vocabulary. Healer logic can reconcile files and console rows without translating synonyms.

36. Task Complexity Is the Independent Floor

Principle

Complexity and quota govern different execution dimensions. Complexity sets the minimum model and thinking effort required by the task. Quota governs the dimensions where headroom matters: parallelism and retry budget.

Conflating the two creates bad behavior in both directions. Abundant budget should not make a trivial rename run through maximum reasoning. Budget pressure should not lower a hard diagnostic below the capacity it needs to succeed.

Applied in CocoPlus

Pre-dispatch complexity estimation writes a run tier, harness compositing preserves model and effort floors, and CocoMeter ACRR shows whether task classes are being under- or over-provisioned.

37. Ambiguity Is Pre-Payable

Principle

Every ambiguity in a task description is a cost that will be paid. Resolve it before dispatch and the cost is essentially zero. Leave it for the agent to discover during execution and the cost becomes model tokens, inspected files, and exploratory turns.

Acceptance checks are the companion discipline. A task that says what done means costs less because the agent knows when to stop. A task without a completion criterion forces the agent to infer the finish line.

Applied in CocoPlus

CocoConsole prompt-quality checks score ambiguity and missing acceptance criteria before dispatch. The warning is non-blocking, but it gives the developer a zero-cost chance to narrow the execution space.

38. The Transcript Is the Source of Truth

Principle

Runtime counters are useful, but they are derived state. The JSONL transcript is the durable event record for what the session actually did: assistant responses, token usage, served model identity, tool activity, and background-agent events.

When billing, ACRR attribution, or model-tier analysis depends on correctness, CocoPlus reconciles against the transcript. Duplicate assistant messages are deduplicated by stable message ID, with a usage fingerprint fallback, before token totals become authoritative.

Applied in CocoPlus

CocoMeter reconciliation reads the JSONL transcript, deduplicates assistant responses, writes reconciliation-[session-id].json, corrects material token gaps, and records transcript-derived actual model identity.

39. Timestamps Have Provenance

Principle

A timestamp must say what moment it marks. Record-write time, dispatch time, start time, and completion time are not interchangeable, especially for background work that may finish long after it was launched.

For background CocoPods, a tool_result timestamp may describe dispatch rather than completion. CocoPlus prefers completion records from queue events when available and labels fallback timestamps explicitly when the authoritative event is missing.

Applied in CocoPlus

CocoFlow flow-state pod records include completion_source and completion_timestamp_reliable so dashboards, duration calculations, and cost attribution can distinguish queue-derived completion from fallback timestamps.

40. Producers Never Grade Themselves

Principle

An evaluator can only be trusted when it cannot silently rewrite the thing it evaluates. Separate context windows help, but they are incomplete if the critic still has write access to the artifact under review.

Quality judgment requires structural separation: producer roles generate, critic roles inspect, and any required signoff is recorded as evidence rather than implied by the producer's confidence.

Applied in CocoPlus

CocoFleet goal-decomposition mode requires critic tasks to declare tool_set: "read_only", records producer and critic roles separately, and treats required critic PASS signoff as a completion condition.

41. Gate Weakening Requires a New Run

Principle

A governance gate declared before a run starts is not a negotiable mid-run preference. Weakening it through an inbox message bypasses the deliberate risk decision that made the gate meaningful.

If the operator wants a different risk posture, that change belongs in committed run policy and a new run. The audit trail should show that a policy changed before execution, not that a running system was talked around its own guardrails.

Applied in CocoPlus

CocoFlow snapshots [run_policy] before dispatch, drains STEER.md before stage transitions, refuses gate-weakening steer messages at the processing layer, and logs refusals to CocoAudit.

42. Stable API Surface for Unstable Conditions

Principle

Some runtime conditions are inherently unstable: permission prompts, provider wording, live policy posture, and background completion timing can all change without warning. Governance should not depend on parsing those unstable surfaces.

A stable API surface records the facts the system owns: which tool opened, which session it belonged to, when it opened, and whether a matching completion record closed the bracket. Human-readable text remains useful context, but it is not the classifier.

Applied in CocoPlus

PreToolUse writes session/open-pre-tool-use.json, PostToolUse closes the matching record, and Notification classifies permission-blocked events from that open set instead of scraping notification wording.

43. Skill Is Memory

Principle

A skill is not only an invocation surface. It is a compact memory contract: when to load a topic, what evidence is required, what files are authoritative, and what must never be inferred from ambient context.

Institutional learning scales when memory is routed through topic skills and schema-declared files rather than poured into standing instructions. The system should know where wisdom lives, but it should load the content only when the task needs it.

Applied in CocoPlus

CocoWisdom defaults to progressive disclosure. $wisdom get <topic> loads a specific category on demand, while Stop-hook distillation writes durable topic files and queues contradictions for review.

44. Negative Memory Is Load-Bearing

Principle

A memory system that records only successful approaches will re-explore failed paths. The cost is not just wasted tokens — it is lost time, repeated failure, and weakened operator trust when the system proposes the same thing that did not work before.

Rejected approaches are first-class memory citizens. The reason an approach was abandoned is exactly the signal the next session needs before trying it again. Negative memory requires judgment, so it should be explicit, durable, and never silently collapsed into positive guidance.

Applied in CocoPlus

CocoWisdom's do-not-use.md is a primary read at session start, not an optional supplement. CocoHygiene does not auto-prune rejection records, and the distillation pipeline routes failure patterns to negative memory as a first-class output.

45. Lexical Baseline Before LLM Processing

Principle

Before adding an LLM step to retrieval or analysis, establish the lexical baseline. Fast text search over existing artifacts is cheap, local, explainable, and strong enough that any semantic layer must earn its place with measurement.

"It must be better because it uses AI" is not evidence. The baseline is a number; the improvement must also be a number. If deterministic matching recovers the needed evidence, the deterministic path is the correct first response.

Applied in CocoPlus

$wisdom recall begins with lexical search over curated wisdom and session indexes. Before CocoRecall or CocoWisdom adds a semantic or synthesized layer, the exact and close-match baseline must be measured and preserved.

46. Structural Correctness ≠ Intent Alignment

Principle

A function can compile, run, return the right type, and pass automated checks while still failing the operator's intent. Structural testing answers "does it work?" Intent alignment answers "does it do what was asked?" Both are required.

Evaluation paths should be explicit about which question they verified. A structural PASS does not mean the work answered the request unless intent alignment was also checked or the gap was consciously accepted.

Applied in CocoPlus

CocoContract's structural gates are necessary but not sufficient; intent-match evaluation answers whether the agent understood the request. For judgment-heavy outputs, observability reads the artifacts CocoFlow already writes instead of requiring special instrumentation from skill authors.

47. Structure Is the Reliability Gap

Principle

Agents default toward fluency, recency, and optimism when important decisions are left unstructured. Across repeated sessions, the same reasoning conducted through a checklist, gate, or named framework is more reliable than free-form advisory judgment.

The reliability gap appears before dispatch, during verification, and at first operation. Pre-mortems recover failure scenarios that forward-only reasoning misses. Verification gauntlets prevent "looks correct" from substituting for evidence. First-run gates prevent silent defaults from becoming operational assumptions.

Applied in CocoPlus

CocoPilot uses pre-mortem and first-run configuration gates, while CocoContract uses risk-scaled tiers, mutation verification, and six honesty rules so unverified work cannot be laundered into a passing verdict.

48. Manifest-First Loading

Principle

Memory should be routed before it is read. A manifest that maps task type to file set keeps context small, explainable, and repeatable; retrieval is not a substitute for knowing which sources are appropriate for the job.

The right default is names first, content only when routed. This preserves awareness without paying the token and attention cost of speculative preload.

Applied in CocoPlus

CocoWisdom reads SCHEMA.md stage mappings to preload only positive topics relevant to the current stage. Unmapped topics remain available through $wisdom get <topic>, while do-not-use.md remains universal.

49. Explicit Curation Over Automatic Accumulation

Principle

Durable memory is a judgment, not a transcript dump. Automatic capture can identify candidates, but permanent project knowledge needs a reason, an evidence pointer, and a reviewable shape.

Systems that remember everything eventually make every future session carry yesterday's noise. Curation is the discipline that lets memory stay useful.

Applied in CocoPlus

CocoWisdom distillation writes schema-declared candidates and queues contradictions for review. Permanent constraints, rejected approaches, and stable lessons are Markdown records with explicit rationale.

50. Git-Native Memory

Principle

Project memory should branch, diff, review, and revert with the project itself. A memory change on a feature branch is part of that branch's claim about reality; it should not leak into main before the work merges.

Plain files make institutional knowledge inspectable by humans and portable across agent runtimes.

Applied in CocoPlus

CocoWisdom, CocoContext, and CocoGrove use branch-scoped memory in Markdown and JSONL files. Git provides the audit trail, review boundary, and rollback mechanism.

51. Air-Gap Compatible by Default

Principle

Enterprise data teams often work where cloud memory services, external indexes, and opaque dependencies require security review. Local Markdown and deterministic indexes are not just simpler; they are deployable in restricted environments.

A feature that can work offline should work offline by default. Networked or semantic layers must be opt-in and justified by measured value.

Applied in CocoPlus

$wisdom index builds a local lexical index, redacts credentials before storage, and leaves raw transcripts unchanged. CocoPlus memory remains air-gap compatible unless a project explicitly enables external services.

Principles are only principles when they are applied in the cases where violating them would be convenient.
